## Reader summary

READER 1 result: the shared UBWC configuration object that both the Adreno 840 (encoder) and the DPU/MDSS (decoder) consume is, for this specific unit, numerically identical to stock's SDE/GPU settings on every field mainline programs. (1) drivers/soc/qcom/ubwc_config.c maps qcom,kaanapali to ubwc_6_0_hbb16 (UBWC 6.0 = 0x60000000, highest_bank_bit 16); the file and smem_dramc.c are untouched by the queue. (2) The SMEM HBB override is NOT applied on the tablet: every mainline run logs "qcom-smem 81d00000.smem: Found an unknown type of DRAM info struct (size = 872)", so smem_dram_parse() returns -EINVAL, __dram stays NULL, qcom_smem_dram_get_hbb() returns -ENODATA and qcom_ubwc_config_get_data() silently returns the static table entry (HBB 16). (3) Stock: qcom,sde-highest-bank-bit = <8 3 7 2> is (DDR type, register field) pairs where the field is HBB-13 (the MDSS UBWC_STATIC HIGHEST_BANK_BIT field is 3 bits wide, bits [6:4] per mdss.xml, not [15:13]); DDR type 8 = LPDDR5 and 7 = LPDDR4X per smem_dramc.c's enum; this unit is type 8 (stock FDT memory node: ddr_device_type = <0x08>), so stock's HBB is 13+3 = 16 = mainline's 16. (4) Other fields: swizzle stock 6 vs mainline LVL2|LVL3 = 0x6; macrotile stock 1 vs mainline true; ubwc-static stock 1 vs mainline bank-spread bit 3 always set (inference on the stock property's meaning); version stock 0x60000000 / GPU ubwc-mode 6 vs mainline UBWC_6_0 (version tag 5 in UBWC_CTRL_2); GPU min-access-length stock 0x20 (32 B) vs mainline min_acc_len_64b = false. sde-dram-channels = 4 and sde-ubwc-bw-calc-version = 1 have no mainline equivalent. (5) Expected mainline register values for the tablet to verify: MDSS UBWC_STATIC (0x9800144) = 0x103E, UBWC_CTRL_2 (0x9800150) = 5, UBWC_PREDICTION_MODE (0x9800154) = 1; MSM_GET_PARAM HIGHEST_BANK_BIT = 16, UBWC_SWIZZLE = 6, MACROTILE_MODE = 1. (6) The queue's splash take-over re-programs UBWC_STATIC after the deferred MDSS reset and before dpu_kms_hw_init, so no UBWC state is lost. Conclusion: the UBWC config object is a poor candidate for the pink/blocky glitch unless the tablet's register/param dump disagrees with the numbers above; the remaining suspects for READERs 2+ are Mesa's a8xx (a840) UBWC tile layout vs the DPU's UBWC >= 5.0 SSPP decode path (no dedicated 6.0 branch, dpu_hw_sspp.c:321) and 144 Hz bandwidth. Two low-priority kernel follow-ups: support/dump the 872-byte SMEM DDR-info layout so the HBB override actually works, and add a one-line pr_info of the HBB source.

## Reader summary

GPU-side (UBWC writer) offline analysis for the OnePlus Pad 4 pink/blocky GNOME glitch. FACTS: (1) The GPU encoder and the DPU decoder are programmed from one shared config object: `qcom,kaanapali` -> `ubwc_6_0_hbb16` (UBWC 6.0, HBB 16, swizzle LVL2|LVL3=6, macrotile on, AMSBC on, min access 32 B, version tag 5). The SMEM HBB override does NOT happen on this unit: dmesg says "Found an unknown type of DRAM info struct (size = 872)" (smem_dramc.c knows 200/208/224/424/504/536/540/616/620), so `qcom_smem_dram_get_hbb()` returns -ENODATA and both sides keep the static HBB 16. Stock (live FDT) agrees on every documented value: SDE `qcom,sde-ubwc-version = 0x60000000`, `sde-ubwc-swizzle = 6`, `sde-macrotile-mode = 1`, `sde-ubwc-static = 1`, `sde-highest-bank-bit = <8 3 7 2>` (LPDDR5 -> 16, LPDDR4X -> 15); GPU `qcom,ubwc-mode = 6`, `qcom,min-access-length = 0x20` (32 B), `qcom,chipid = 0x44050a01` "Adreno840v2". Computed a840 register values for this config: GRAS_NC_MODE_CNTL 0x60 (BV+BR), RB_CCU_NC_MODE_CNTL 0x46, RB_CMP_NC_MODE_CNTL 0x28046, SP_NC_MODE_CNTL 0x26, TPL1_NC_MODE_CNTL 0x6, RBBM_NC_MODE_CNTL 0x1; MDSS UBWC_STATIC 0x103e, UBWC_CTRL_2 5, UBWC_PREDICTION_MODE 1; SSPP UBWC_STATIC_CTRL 0xC0000000 for ARGB8888 planes. Userspace params on kaanapali: HIGHEST_BANK_BIT 16, UBWC_SWIZZLE 6, MACROTILE_MODE 1, CHIP_ID 0xfc44050a31 (= DT 0x44050a01 | 3 slices << 4 | speedbin fuse 0xfc << 32), GMEM 18 MiB, GMEM_BASE 0, UCHE_TRAP_BASE 0x1fffffffff000, MAX_FREQ 1.2 GHz. All five NC_MODE registers sit in CP-protected ranges, so Mesa cannot alter the encoder config on a840: the kernel values above ARE the encoder config. No patch in the queue touches drivers/gpu/drm/msm/adreno, ubwc_config.c or smem_dramc.c; the only queue changes near this path are the msm_mdss.c splash/takeover refactors (UBWC re-setup at takeover) and the DPU DSC width patch. (2) "UBWC 6.0 treated as 5.x": the a8xx code differs from 5.0 only by yuvnotcomptofc (YUV only, irrelevant to RGB); the DPU SSPP has no 6.0 branch at all (`>= UBWC_5_0` path, BIT(30)|BIT(31) for RGB non-DX) and the MDSS 6x path only differs by the tag value 5. The one asymmetry inside the shared version logic that can bite RGB scanout: the GPU sets rgba8888_lossless only for 4.0<=v<5.0 (so OFF for 6.0) while the DPU SSPP sets the extra BIT(31) for every RGB non-DX plane at >=5.0; whether these two bits describe the same feature cannot be verified offline (no downstream sde/kgsl source on this machine). (3) The DPU derives the UBWC buffer layout itself (meta plane at fb->offsets[0], pixel plane at +round_up(round_up(ceil(w/16),64)*round_up(ceil(h/4),16),4096), pixel pitch round_up(w*bpp,256)) and ignores fb->pitches/offsets[2] for UBWC; for 2400x3392 ARGB8888 that is meta 163840 B and pitch 9728 B. If Mesa's gen8 layout differs in any constant, the DPU reads pixel data from the wrong offset -> tile-granular garbage while linear fbcon is clean. This is the highest-yield thing the tablet run can settle with `/sys/kernel/debug/dri/*/framebuffer`. (4) IFPC is enabled on a840 (ADRENO_QUIRK_IFPC) and all NC_MODE registers are covered by the IFPC/pwrup/dynamic restore lists, captured from live values after hw_init; no module parameter disables IFPC, but MSM_PARAM_SYSPROF blocks it (a6xx_gmu.c:2103), which gives a runtime A/B test. Overall: no GPU-vs-DPU config mismatch is visible in source; the remaining candidates on the GPU side are (a) the Mesa gen8 UBWC layout vs the DPU's fixed layout formula, (b) the SSPP BIT(31)/rgba8888_lossless asymmetry, (c) an IFPC-restore race, in that order.
